# Type System Discipline

Make the type checker reject impossible states, mismatched primitives, and unhandled variants. Prefer designs that define errors and special cases out of existence over adding a handler for each one.

- **Make illegal states unrepresentable.** Model variants as sum types (discriminated unions, enums with payloads, sealed classes or interfaces), not as a bag of optional fields where contradictory combinations type-check. A record with a `completed` flag and an optional `completedAt` date admits `completed` with no date. Derive the flag from the date, or model the two states as separate variants. If you can write a comment explaining when a combination of fields is valid, split it into a sum type. In a language without sum types, use an interface that only this module can implement.
- **Give semantic primitives their own types.** `UserId` and `OrderId` are strings underneath but should not be interchangeable. Give each a wrapper or branded type that the type checker treats as distinct. Validate once at creation, and trust the type downstream. If two arguments share a primitive type but mean different things, give them distinct types.
- **External data is untyped until parsed.** RPC payloads, JSON, IPC messages, CLI args, config files, environment variables, database rows. Have a parse function at every boundary that turns unstructured input into the typed model. `boundary-discipline.md` says where to put validation.
- **Don't use casts to override the type checker.** Casts, unchecked type assertions, forced unwraps, and assertion functions that bypass the type checker are runtime crashes waiting to happen. If the type checker can't prove a fact, prove it yourself by validating, narrowing, or refining the model. If you can't, treat the cast as a known hazard. Trace each one to the boundary and validate there.
- **Make the type checker catch unhandled variants.** A match on a sum type must fail the build when a new variant is added without handling, so the build tells the next agent where to add a case. Use an exhaustive match, or a check in the default branch that fails to type-check when a variant is unhandled. Where the type checker cannot check exhaustiveness, add a linter that does and run it in CI.
- **Derive types from authoritative schemas.** When a protocol buffer, OpenAPI spec, GraphQL schema, database migration, design-token file, or another file owns a shape, derive from it instead of hand-rolling a parallel type. See `encode-lessons-in-structure.md`.
- **Tighten a type only where a function is partial.** A runtime assertion, null check, or "this should never happen" throw marks the place a type is too weak. Push that check up into the type. Then stop. The type system's job is to track the cases each use site must handle, not to describe the data as precisely as possible. Prefer total functions: the sum of an empty list is 0, so `sum` takes a plain list, but the first item of an empty list has no answer, so `head` takes a non-empty one. If nothing would otherwise fail at runtime, keep the plain type.
